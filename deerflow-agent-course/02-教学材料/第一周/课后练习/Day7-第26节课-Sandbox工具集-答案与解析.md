### 1.2 判断题答案与解析

**1. (❌) 进程隔离通过Linux的cgroups和namespaces技术实现，与容器隔离技术基础相同。**

**解析**: 错误。进程隔离主要通过操作系统的资源限制（resource模块）实现，不依赖于cgroups和namespaces。容器隔离才使用cgroups和namespaces技术。进程隔离是更轻量级的限制。

**2. (✅) 命令注入防护只需要检查命令参数，不需要检查命令本身。**

**解析**: 正确。`_validate_command`方法检查命令的所有部分（包括命令本身和参数），因为攻击者可能通过命令参数注入恶意代码。例如`echo "hello; rm -rf /"`中，参数包含危险字符。

**3. (✅) PythonTool的`_check_code_safety`方法除了检查导入语句，还会检查危险函数和系统调用。**

**解析**: 正确。`_check_code_safety`方法调用`_check_imports`检查导入，同时检查`exec`、`eval`、`__import__`等危险函数，以及`os.system`、`subprocess.`等系统调用模式。

**4. (❌) DockerSandboxProvider的`_collect_docker_stats`方法可以实时监控容器资源使用。**

**解析**: 错误。`_collect_docker_stats`方法在命令执行后调用`docker stats --no-stream`获取一次性的资源统计，不是实时监控。实时监控需要持续运行`docker stats`命令。

**5. (✅) 资源限制设置只在子进程生效，父进程不受影响。**

**解析**: 正确。`_set_resource_limits`方法通过`preexec_fn`在子进程中调用，资源限制只应用于子进程，父进程的限制保持不变。

**6. (✅) 沙箱工具的异常处理应该尽可能捕获所有异常，防止异常传播到外部系统。**

**解析**: 正确。沙箱工具应该将异常封装为工具执行结果的一部分，防止沙箱内的异常影响外部系统的稳定性。

**7. (❌) SecurityPolicy的`read_only_fs`设置为True可以完全防止文件系统修改。**

**解析**: 错误。虽然`read_only_fs`设置为True可以防止大多数文件系统修改，但仍有绕过方法，如使用内存文件系统（tmpfs）、共享内存、或通过proc/sys文件系统修改内核参数。完全防止文件系统修改需要多层防御。

**8. (✅) BashTool的`validate_parameters`方法会检查命令是否在允许的命令列表中。**

**解析**: 正确。`validate_parameters`方法调用`security_policy.is_command_allowed(command)`检查命令是否在允许列表中。

**3. 解释命令注入攻击的原理，并说明BashTool中`_validate_command`方法如何防止命令注入。提供至少三种额外的防护措施。**

- 防护措施多层次 (1分)

**参考答案**:
**命令注入原理**: 攻击者通过输入数据向系统命令中注入恶意命令，利用程序拼接命令字符串的漏洞。例如：`os.system("echo " + user_input)`，如果user_input是`hello; rm -rf /`，则执行两条命令。

**`_validate_command`防护**: 方法使用正则表达式检测危险字符（&、|、;、`、$()等），发现则拒绝执行。但仅检查字符存在局限性，可能被编码、变形绕过。

**额外防护措施**:
1. **参数化执行**: 使用`subprocess.run([command, arg1, arg2])`而不是字符串拼接，确保参数不被解析为命令。
2. **最小权限原则**: 以非特权用户运行沙箱，限制文件系统访问权限。
3. **输入验证和过滤**: 对用户输入进行严格验证，只允许预期字符集。
4. **输出编码**: 对命令输出进行适当编码，防止输出中的恶意内容被误执行。
5. **审计和日志**: 记录所有命令执行，便于事后分析和攻击检测。

**5. 说明资源限制机制的工作原理，包括CPU时间、内存、磁盘、进程数等资源的限制方法和限制精度。**

**📝 评分要点** (满分5分):
- 每种资源限制方法正确 (1分/资源，共4分)
- 限制精度分析合理 (1分)

**参考答案**:
1. **CPU时间限制**: 使用`resource.RLIMIT_CPU`设置进程的最大CPU时间（秒）。精度：秒级，实际限制由操作系统内核调度器实施，精度受调度粒度影响。
2. **内存限制**: 使用`resource.RLIMIT_AS`设置进程的虚拟内存地址空间大小。精度：字节级，但实际物理内存使用可能因共享内存、内存映射文件而复杂。
3. **磁盘限制**: 使用`resource.RLIMIT_FSIZE`设置进程创建的文件最大大小。精度：字节级，但只限制单个文件大小，不限制总磁盘使用。
4. **进程数限制**: 使用`resource.RLIMIT_NPROC`设置进程可以创建的最大子进程数。精度：整数计数，包括所有子进程。

**限制精度分析**:
- **软限制和硬限制**: 每个资源有软限制（当前限制）和硬限制（最大可设限制）
- **内核实施**: 限制由操作系统内核强制实施，用户态程序无法绕过
- **资源类型差异**: CPU时间限制相对精确，内存限制受页面交换影响，磁盘限制只针对单个文件
- **副作用**: 达到限制时，进程会收到信号（如SIGXCPU、SIGSEGV）或被终止

**6. DockerSandboxProvider如何实现容器隔离？包括哪些隔离维度（文件系统、网络、进程、用户等）？**

**📝 评分要点** (满分5分):
- 容器隔离原理清晰 (2分)
- 隔离维度全面 (2分)
- 理解Docker安全特性 (1分)

**参考答案**:
**容器隔离原理**: Docker使用Linux内核的cgroups（控制组）和namespaces（命名空间）技术实现进程级虚拟化。cgroups限制资源使用，namespaces提供隔离视图。

**隔离维度**:
1. **进程隔离** (PID namespace): 容器有自己的进程ID空间，看不到主机和其他容器的进程
2. **网络隔离** (Network namespace): 容器有自己的网络栈、IP地址、端口空间，可通过`--network none`完全隔离
3. **文件系统隔离** (Mount namespace): 容器有自己的根文件系统，可通过`--read-only`设为只读
4. **用户隔离** (User namespace): 容器内的root用户映射到主机非特权用户，防止权限提升
5. **主机名隔离** (UTS namespace): 容器有自己的主机名和域名
6. **进程间通信隔离** (IPC namespace): 容器有自己的System V IPC和POSIX消息队列
7. **资源限制** (cgroups): 通过`--memory`、`--cpus`等参数限制CPU、内存、磁盘I/O等资源

**安全特性**:
- **安全计算模式** (seccomp): 限制系统调用
- **能力控制** (Capabilities): 细粒度的特权控制
- **AppArmor/SELinux**: 强制访问控制

**7. 沙箱工具的异常处理策略应该包括哪些方面？如何处理超时、资源耗尽、权限拒绝等异常场景？**

**📝 评分要点** (满分5分):
- 异常处理策略全面 (2分)
- 具体场景处理方案合理 (2分)
- 优雅降级思想 (1分)

**参考答案**:
**异常处理策略**:
1. **预防性检查**: 执行前检查资源可用性、权限充分性
2. **防御性编程**: 假定所有外部调用都可能失败，添加适当错误处理
3. **资源隔离**: 确保单个沙箱故障不影响其他沙箱
4. **优雅降级**: 当高级功能失败时，提供基本功能或明确错误信息
5. **审计日志**: 记录所有异常，便于问题诊断和系统改进

**具体场景处理**:
- **超时处理**: 使用`subprocess.TimeoutExpired`异常捕获，终止进程，返回超时错误结果，记录执行时间
- **资源耗尽**: 通过资源限制提前预防，达到限制时进程被终止，返回资源不足错误，建议调整资源配额
- **权限拒绝**: 执行前检查所需权限，使用最小权限原则，失败时返回权限错误，提示所需权限
- **命令不存在**: 执行前验证命令路径，捕获`FileNotFoundError`，返回命令未找到错误
- **语法错误**: 代码执行前可进行语法检查，捕获`SyntaxError`，返回语法错误信息
- **网络异常**: 检查网络访问权限，捕获连接超时、拒绝连接等异常，返回网络错误

**8. 设计一个多层防御的沙箱系统，说明如何组合不同的安全措施（如静态分析、动态监控、资源限制、行为检测等）提供纵深防御。**

**📝 评分要点** (满分5分):

- 安全措施组合合理 (2分)
- 纵深防御架构完整 (2分)

**参考答案**:
**多层防御沙箱系统设计**:

**第一层：输入验证和过滤**
- 白名单验证：只允许预期的字符集和模式
- 语法检查：验证代码语法正确性
- 长度限制：防止过大的输入消耗资源

**第二层：静态代码分析**
- 导入检查：验证模块在白名单中

def _set_resource_limits(self):
    """设置资源限制（在子进程中调用）"""
    import resource
    
    # CPU时间限制
    resource.setrlimit(
        resource.RLIMIT_CPU,
        (self.security_policy.max_cpu_seconds, 
         self.security_policy.max_cpu_seconds)
    )
    
    # 内存限制
    memory_limit = self.security_policy.max_memory_mb * 1024 * 1024
    resource.setrlimit(
        resource.RLIMIT_AS,
        (memory_limit, memory_limit)
    )
    
    # 进程数限制
    resource.setrlimit(
        resource.RLIMIT_NPROC,
        (self.security_policy.max_processes, 
         self.security_policy.max_processes)
    )
    
    # 文件大小限制
    file_size_limit = self.security_policy.max_disk_mb * 1024 * 1024
    resource.setrlimit(
        resource.RLIMIT_FSIZE,
        (file_size_limit, file_size_limit)
    )
    
    # 文件描述符限制 - 防止打开过多文件
    # 软限制1024，硬限制2048，允许进程适度增加但有限制
    resource.setrlimit(
        resource.RLIMIT_NOFILE,
        (1024, 2048)  # (软限制, 硬限制)
    )
    
    # 核心文件大小限制 - 禁止生成核心转储文件
    # 核心转储可能包含敏感信息，且可能被攻击者利用

        resource.RLIMIT_CORE,
        (0, 0)  # 软硬限制都设为0，完全禁止
    )

4. **可解释性模块设计** (3分):
   - 模型决策解释（特征重要性、决策规则等）
   - 用户可理解的解释输出
   - 解释准确性和可信度评估

5. **性能优化方案** (3分):
   - 模型推理性能优化（量化、剪枝等）
   - 特征提取性能优化
   - 系统整体性能影响控制

**参考答案要点**:
- **特征**: 基于AST的代码特征，系统调用序列，资源使用模式
- **模型**: 使用LightGBM或神经网络的异常检测模型
- **策略调整**: 基于置信度的策略升级，渐进式严格化
- **可解释性**: SHAP值分析，决策规则提取
- **性能**: 模型轻量化，异步推理，缓存热点决策
